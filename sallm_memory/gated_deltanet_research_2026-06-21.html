Gated DeltaNet Research for SALLM

Literature review and go/no-go recommendation for MzansiLM-style low-resource pretraining. Created 2026-06-21. Research only: no SLURM jobs, no training-code edits.

Recommendation: do not spend a full SALLM pretraining run on Gated DeltaNet next. GDN is worth a small FLA-based hybrid feasibility screen, but HGRN2/BabyHGRN still has the stronger direct low-resource/sample-efficiency case.

Full Run

No-go for now.

Small Screen

Go, if compute is available.

Preferred Shape

Hybrid GDN plus periodic attention.

What Gated DeltaNet Is

Gated DeltaNet is a linear-attention / recurrent-memory architecture. It keeps a fixed-size matrix state instead of a growing softmax-attention KV cache. DeltaNet updates this state with a delta rule: before writing a new value at a key, it subtracts the current value read from that key, giving targeted overwrite instead of plain accumulation. Gated DeltaNet adds Mamba2-style decay/gating, so the state can forget broadly and edit a selected association.

Architecture Comparison

Architecture Memory mechanism SALLM implication
Transformer attention Token-level access to past keys and values. Best default for copying, source-conditioned generation, and prompt use; heavier memory cost.
DeltaNet Fast-weight matrix memory with delta-rule targeted overwrite. Mechanism directly targets associative interference.
Gated DeltaNet Delta-rule memory plus Mamba2-style adaptive decay. Plausible fit for Mamba's source-preservation gap, but not proven for low-resource SA languages.
Gated DeltaNet-2 Separate erase and write gates over channels. Stronger newer evidence, but newer code path and no direct SALLM fit yet.
RetNet Retention with parallel, recurrent, and chunkwise modes. Useful related work, less directly tied to source-copy failures.
Mamba / Mamba-2 Selective SSM / SSD recurrent state. SALLM has already seen source-preservation and generation-loss gaps.
RWKV RNN-like dynamic recurrence and matrix-valued states. Mature efficient-LM family; lower priority than HGRN2/GDN screen.
xLSTM Exponential gates plus scalar or matrix memory. Already promising versus Mamba locally, still behind LLaMA on clean generation loss.
HGRN / HGRN2 Gated linear recurrence with state expansion. Best direct low-resource/sample-efficiency evidence via BabyHGRN.

Evidence Table

Evidence What it says SALLM relevance
GDN paper, ICLR 2025 GDN combines Mamba2 gating with DeltaNet updates and reports better LM, reasoning, retrieval, length extrapolation, and long-context results than Mamba2 and DeltaNet. Strong reason to screen. Not direct low-resource evidence.
Official GDN repo Code exists; FLA is recommended for faster kernels and varlen training. The standalone repo gives no pretrained weights and notes evaluation inconvenience before HF/FLA conversion. Integration is doable, but not drop-in for SALLM.
GDN-2, 2026 At 1.3B/100B FineWeb-Edu, GDN-2 beats Mamba-2, GDN, KDA, and Mamba-3 variants on average LM, reasoning, and retrieval. Biggest gains are RULER multi-key retrieval. Best technical evidence for the family, but no low-resource SA evidence.
Qwen3-Next Production-scale hybrid: 48 layers repeat 3 GDN blocks then 1 gated-attention block; 262K native context, extendable to about 1M. Industry validation favors hybrid GDN, not pure GDN.
Kimi Linear KDA extends GDN with finer-grained gating and reports full-attention-beating hybrid results with large training runs. Supports the direction, but points to KDA/GDN-2 rather than vanilla GDN.
Copying/SSM literature Transformers have an advantage on exact copying because fixed-state models compress context; Mamba hybrids recover more than pure SSMs on retrieval tasks. T2X and AfriHG need source preservation, so pure fixed-state GDN is risky.
BabyHGRN HGRN2 outperforms transformer baselines in 10M/100M word BabyLM tracks across BLiMP, EWoK, GLUE, and BEAR. Stronger direct sample-efficiency evidence than GDN for low-resource thesis framing.
Local SALLM state Existing repo has Mamba, Mamba2-hybrid, xLSTM, and RWKV configs; no FLA/GDN dependency or config. A GDN run needs an integration spike and must be judged against Mamba/xLSTM/LLaMA gates.

Low-Resource Fit

Evidence for GDN data efficiency is suggestive, not proven. GDN and GDN-2 show better loss and recall than nearby efficient architectures at 400M/1.3B and 100B-ish token regimes, but that is not the same as low-resource South African-language pretraining.

The positive SALLM hypothesis is narrow: targeted overwrite may reduce interference in compressed memory and improve source entity/value preservation compared with Mamba. The counter-hypothesis is equally important: if exact copying from prompt context is the bottleneck, GDN may still lose to LLaMA unless attention layers are retained.

No reviewed paper makes a direct claim that GDN is unusually good for South African languages, morphology, MzansiText-style mixtures, T2X, or AfriHG. Treat morphology benefits as hypotheses.

Implementation Risks

  • Dependency gap: SALLM currently depends on transformers, mamba-ssm, and xlstm, not fla-core.
  • Code path: the practical route is FLA-first, not a bespoke port of standalone NVLabs code.
  • License: NVLabs GDN/GDN-2 repos use NVIDIA Source Code License-NC; FLA is MIT.
  • Kernels: performance depends on Triton/FLA-style kernels. Unsupported hardware paths may be slow or incomplete.
  • Evaluation: official notes flag generation/evaluation inconvenience and prompt sensitivity.
  • Stability: GDN-2 uses fp32 decay/state choices and precision-sensitive solves; BF16 parity needs checking.
  • Checkpoints: no official pretrained GDN weights are released, so SALLM would train from scratch.
  • Context length: strongest GDN-family wins are long-context retrieval; a 2048-only SALLM run may under-test the architecture.
  • Tokenizer: GDN does not solve tokenization. Keep the same 65K ByteLevel BPE for fair comparison.

Hypotheses To Test

  1. A 125M-ish GDN hybrid should beat current Mamba base validation loss by 10K steps and not trail xLSTM by much.
  2. On clean T2X Xho, AfriHG Xho, and AfriHG Zul teacher-forced gates, GDN should be closer to xLSTM/LLaMA than to current Mamba.
  3. After tiny downstream adaptation, GDN should improve source entity/value coverage over Mamba by at least 20% relative without lowering chrF.
  4. GDN plus periodic attention should beat pure GDN on source-copy and prompt-conditioned tasks.
  5. GDN should improve MasakhaPOS constrained token accuracy or exact-length sequence behavior over Mamba.
  6. GDN must have acceptable tokens/sec and memory versus Mamba2-hybrid and xLSTM.

Smallest Defensible Experiment Plan

  1. Integration spike: branch-only FLA dependency; instantiate one 125M-ish GDN model with SALLM vocab; verify forward/backward, BF16, generation, save/load, and eval route.
  2. Cheap base screen: train one GDN hybrid for the same budget as previous 10K screens, using the same tokenizer, splits, optimizer family, and clean-loss probes.
  3. Gate criteria: continue only if base validation and clean conditional loss clearly beat Mamba and are at least competitive with xLSTM.
  4. Full-run decision: full GDN pretraining is a go only if the screen passes base loss, clean generation loss, source preservation, and throughput.

Final Call

  1. Finish and interpret current xLSTM gates.
  2. Prioritize HGRN2 if the goal is low-resource/sample-efficiency evidence.
  3. Run GDN only as a bounded hybrid feasibility screen aimed at the known Mamba source-preservation gap.
  4. Prefer FLA GDN for maturity; keep GDN-2/KDA as a later refinement if vanilla GDN integration is easy and the first screen is positive.
