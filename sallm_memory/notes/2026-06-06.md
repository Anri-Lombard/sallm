### xLSTM POS vs NER interpretation and HPO direction

- Inspected the active xLSTM POS/NER fine-tuning and eval configs.
- Likely reasons POS is much stronger than NER:
  - POS evaluation is token-aligned and uses token accuracy; NER evaluation uses generated `label: entity` spans and exact span F1 after parsing.
  - POS is closed-class and dense: every input token gets one of a small set of labels.
  - NER is sparse and boundary-sensitive: the model must identify rare spans, copy the exact surface form, choose the entity type, and emit the expected delimiter format.
  - The monolingual xLSTM POS recipe is stronger than the monolingual NER recipe: POS uses LoRA `r=128`, `alpha=256`, embeddings targeted, lower weight decay, and no gradient checkpointing; Xhosa NER uses LoRA `r=16`, `alpha=32`, no embeddings target, high weight decay, and larger effective batch.
- Important caution:
  - Multilingual NER already uses the stronger `r=128`/embedding-target style and remains modest, so recipe differences alone probably do not explain the full gap to LLaMA.
- Best next experiment direction:
  - First test NER as a token/BIO tag-sequence task, because xLSTM clearly handles POS-style token-aligned labelling well.
  - Then run a small NER HPO grid around LoRA capacity, weight decay, LR, warmup, and output formulation rather than a broad blind sweep.
