## Base-First Decision

User asked whether the remaining work should keep pushing monolingual and
multilingual downstream recovery, or first improve the base model.

Decision:

- The current best path is base-first, then downstream recovery.
- Reason: downstream Mamba is not uniformly bad. MasakhaNews parity is strong,
  checkpoint-selected T2X and AfriHG improved, and some monolingual recovery
  gates beat earlier weak runs. However, the clean base audits show the Mamba
  base itself is much weaker than the LLaMA base under the same tokenizer and
  validation prompts.
- Because both monolingual and multilingual downstream gates are downstream of
  the same base-quality bottleneck, continuing to tune monolingual/multilingual
  fine-tuning now risks overfitting around a bad base rather than resolving the
  root cause.
- The immediate objective is therefore not to declare Mamba failed, and not to
  switch to hybrid yet. It is to find a stronger pure-Mamba base recipe/shape.
- Once a stronger pure-Mamba base candidate closes a meaningful portion of the
  base-loss gap, rerun the downstream gates in this order:
  1. clean generation-loss audit on T2X/AfriHG validation,
  2. small full fine-tune on the most diagnostic generation task,
  3. monolingual vs multilingual AfriHG/T2X comparison,
  4. POS/NER output-shape rescue only after generation base quality is less
     confounded.

Best next experiment:

- Run a pure-Mamba2 120-130M shape/recipe gate closer to public Mamba2-130M:
  wider/shallower, `expand=2`, `state_size=128`, and otherwise matched data,
  tokenizer, optimizer family, and audit harness.
- Compare it directly against the failed 20k `expand=4/state_size=64` run on:
  held-out pretraining loss trajectory, clean generation-loss PPL, runtime, and
  scratch footprint.
