xLSTM HPO plan for mono, multi, and general downstream adapters

Review plan before any new HPO submission. The goal is to improve xLSTM where tuning can plausibly help, without repeating the POS/NER evaluation mistakes or tuning directly on official test rows.

Short Answer

Do not run one giant cross-task sweep for everything. Run task-specific HPO for mono and multi adapters, then run a separate general-adapter HPO where the objective is deliberately across tasks. In other words: mono/multi HPO is mostly within one task at a time; general HPO is across tasks by design.
Mono

One task, one language. Use this to find sharp task-language recipes and diagnose whether a language is the bottleneck.

Multi

One task, multiple languages. Use this for the main benchmark recipe because it is closest to the multilingual comparison table.

General

Multiple tasks, multiple languages, one adapter. This is the only stage where HPO should be across tasks.

Why This Shape

Problem What we learned HPO implication
POS looked excellent before, then corrected evaluation lowered it. Old lm-eval list-target setup inflated token accuracy. Correct constrained POS is real but lower: xLSTM about 0.69-0.73 by language. POS is the best first HPO target, but selection must use constrained validation scoring.
NER remains very poor even after BIO tag-sequence reformulation. All architectures collapse under legal closed-label BIO scoring. xLSTM macro entity F1 is only 0.0367. Do not spend broad HPO budget on NER first. Use NER as a diagnostic gate, not the main objective.
T2X and AfriHG are weak for xLSTM. Mixed-source rescue and decode sweeps did not produce a strong official test result. Pure HPO may help a little, but source/structure interventions should be tested before a large sweep.
General adapter collapsed on structured tasks. The single adapter is not just under-tuned; it may need mixture/task weighting and objective balancing. General HPO should tune mixture and task balance, not only LR and LoRA settings.

Objective Design

POS Multi Objective

Main score = mean constrained validation token accuracy across Tswana, Xhosa, and Zulu. Tie-breakers are exact sequence accuracy, balanced per-language score, and lower confusion concentration.
Gate Reason Fail condition
Per-language floor Prevents a run from winning by improving one language while damaging another. Any language drops more than roughly 1-2 points versus current xLSTM constrained baseline.
Prediction label distribution Detects label-prior collapse. One or two labels dominate beyond a sensible threshold, even if token accuracy improves.
Exact sequence tie-break Token accuracy can hide broken sentence-level behavior. Higher token accuracy but worse exact sequence and worse examples.

General Adapter Objective

This is the only genuinely cross-task HPO objective. Use a weighted validation score, not a single task's metric.

Task family Metric Weight Gate
MasakhaNews F1 20% Must not regress badly from current task-specific xLSTM.
MasakhaPOS Constrained token accuracy 30% Must clear a minimum floor; POS is our cleanest structured-token signal.
SIB/Injongo F1/accuracy 25% Must improve over current general adapter, not just task-specific adapters.
NER diagnostic BIO entity F1 / label collapse check 10% Diagnostic only; use as collapse detector, not as primary target.
T2X/AfriHG chrF plus source/semantic sanity 15% Only include if runtime budget allows; otherwise handle in separate structural wave.

Evidence Basis For The Parameters

The parameter families are research-backed. The exact ranges are not copied from one paper; they are a conservative blend of xLSTM training defaults, common LoRA practice, and local SALLM evidence from previous xLSTM/Mamba/POS audits.
Parameter family Evidence tier Backing How it affects our sweep
AdamW, warmup, weight decay, gradient clipping Strong architecture-level support The xLSTM paper trains with AdamW, beta2 0.95, epsilon 1e-5, gradient clipping 1.0, warmup, cosine decay, and weight decay 0.1. Our base xLSTM recipe already follows several of these choices. Keep optimizer family fixed. Tune LR/warmup/weight decay around sensible local ranges instead of searching optimizer variants.
LoRA rank, alpha, dropout Strong PEFT-method support, weaker exact-range support LoRA is paper-backed as a parameter-efficient adaptation method. PEFT/TRL documentation treats rank, alpha, target modules, and dropout as the core LoRA configuration knobs. Tune rank/alpha/dropout, but keep ranges bounded. Use rank 16-128 and alpha tied to rank rather than arbitrary alpha values.
Learning rate range Local + general fine-tuning support Existing SALLM sweeps use 3e-5 to 3e-4. Prior xLSTM configs live around 1e-4 to 5e-4, while task-specific LoRA adaptation often needs lower LR than base pretraining. Use a log-scale LR search. Start with roughly 1e-5 to 5e-4 for POS; narrow after the pilot.
Epoch count Local task evidence POS is a closed-label dense token task and xLSTM already learns nontrivial POS behavior. NER did not improve under reformulation, so longer epochs alone are unlikely to rescue NER. Let POS run longer than generation tasks. Do not infer that the same epoch range should apply to NER/T2X/AfriHG.
Bayesian sweep shape Tooling/practice support W&B Sweeps explicitly supports Bayesian hyperparameter search. The repo already uses W&B Bayesian sweeps for existing HPO configs. Use Bayesian search only after the objective is clean. Keep pilot runs small because W&B sweeps do not magically fix bad metrics.
Per-language and per-task promotion gates Local audit support The POS and NER audits showed aggregate metrics can hide broken behavior or label-prior collapse. Promotion requires per-language floors and confusion checks, not only the top aggregate validation score.

Sources to cite in advisor discussion: Beck et al. 2024 xLSTM; Hu et al. 2021 LoRA; Hugging Face PEFT/TRL LoRA docs; W&B Sweeps docs. Local evidence comes from the corrected constrained POS and NER diagnostics recorded in the 2026-06-16 notes.

Execution Order

  1. Prepare corrected constrained validation evaluators for POS, and confirm they produce the same fields as test evaluators.
  2. Create an xLSTM POS multi HPO sweep that optimizes constrained validation, not old lm-eval list-target accuracy.
  3. Run 8-12 pilot trials on L40S; pull lightweight artifacts and summarize locally.
  4. Promote top 3-4 to full runs; final test only the winner.
  5. If POS improves, run small mono sweeps only for languages that remain weak.
  6. Then run the general adapter HPO with a cross-task objective and collapse gates.
  7. Only after this, decide whether T2X/AfriHG get structural HPO or whether we move to GatedDeltaNet.

What I Would Not Do

Bad plan Why not
Run one 50-trial sweep per existing xLSTM task config immediately. Too expensive, and some objectives are known-broken or low-yield after the eval audits.
Optimize NER first. The BIO diagnostic says the failure is label-prior/calibration collapse, not just a tunable span-output issue.
Tune on official test rows. This would make the spreadsheet results less defensible. Use validation for HPO, test once.
Use old POS lm-eval token accuracy. That path inflated POS before. Use constrained closed-label POS scoring.
Let a single aggregate score hide task collapse. Every promoted config needs per-language and per-task floors.

Decision Needed Before Submission

My recommended first submission is xLSTM POS multi constrained-validation HPO, not general HPO and not NER HPO. After the pilot, we decide whether mono sweeps are necessary or whether the multi recipe is strong enough to promote.
