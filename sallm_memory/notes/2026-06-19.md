- HPO implementation audit, 13:20 SAST:
  - Broad conclusion: the repo's HPO pattern is directionally reasonable, but
    only the constrained POS HPO path is currently defensible end to end for
    xLSTM. Generic xLSTM HPO for SIB/Injongo has implementation issues and
    should not be trusted until patched and smoke-tested.
  - What is correct:
    - `scripts/launch_hpo.sh` creates a W&B sweep and runs `wandb agent` with a
      bounded count, which matches the standard W&B sweep workflow.
    - Each W&B run starts a fresh Python process, loads the base config, applies
      sweep values, creates a fresh model, trains, and logs a configured
      objective.
    - The constrained POS path is much stronger than the generic path:
      `sallm.hpo.constrained_pos_trial` forces final adapter saving, runs the
      corrected closed-label POS validation evaluator after training, writes
      `constrained_pos_validation.json`, and logs
      `hpo/pos_val_token_accuracy_macro`.
    - Validation-HPO results are not promoted directly; selected adapters are
      promoted only after held-out test artifacts prove split/protocol/metric.
  - Normal stochasticity:
    - 4-run Bayesian POS screens are very small; they are useful screens, not
      proof that every mono/multi/general adapter should beat the prior best.
    - Mixed discrete choices such as scheduler, epochs, LoRA rank/alpha/dropout,
      and a narrow learning-rate band can easily produce validation winners that
      do not improve held-out test.
  - Concrete implementation issues:
    - Generic xLSTM HPO sweeps for `xlstm_injongointent_all` and `xlstm_sib_all`
      do not set `training.pad_to_multiple_of=64`. Local logs for `941190` and
      `941191` show failures inside `training_step -> compute_loss ->
      model(**inputs)` with xLSTM chunk assertions (`255` and `276` not
      divisible by `64`). This is not stochastic HPO; it is a bad batch-padding
      contract for xLSTM training.
    - The earlier general POS HPO `937356` failed for a different xLSTM
      generation path: `ShowCompletionsCallback` called stock `model.generate`
      at epoch end and hit sequence length `928` not divisible by chunk size
      `64`. The repaired general sweep now disables completions/generation
      metrics, so that specific issue is patched for `941187`.
    - Generic HPO does not save final adapters unless
      `SALLM_SAVE_FINAL_ADAPTER_FOR_HPO=1` is externally supplied. The POS HPO
      wrapper sets this internally; generic `sallm.hpo.run` does not. This makes
      later held-out evaluation easy to lose or forget.
    - Generic xLSTM SIB/Injongo finetune configs still point at
      `anrilombard/sallm-xlstm-125m`, while current POS HPO uses
      `anrilombard/sallm-xlstm-125m-native-3epoch-20260531`. Unless this is
      intentional, it makes cross-task xLSTM HPO inconsistent with the current
      base result story.
    - Generic HPO has no repeat-seed confirmation for the selected best. This
      is acceptable for cheap screening, but not for final claims when margins
      are small.
  - Minimal next fixes before rerunning non-POS xLSTM HPO:
    - add `training.pad_to_multiple_of: {value: 64}` to every xLSTM generic
      sweep;
    - move xLSTM task configs intended for current comparisons to the 3-epoch
      base checkpoint, or explicitly label old-base sweeps as old-base;
    - either set final adapter saving inside generic `sallm.hpo.run` for HPO, or
      create a tiny classification-HPO wrapper like the POS wrapper;
    - after a sweep selects a winner, run exactly one held-out selected eval
      before updating progress/sheet;
    - for small improvements, rerun the selected config with 2-3 seeds before
      treating it as a stable result.
