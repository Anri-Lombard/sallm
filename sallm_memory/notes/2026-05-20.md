## Mamba Architecture Research Refresh

User asked whether we are missing newer Mamba research or open-source
implementation choices that could make Mamba loss fall faster or produce a
better architecture comparison.

Sources checked:

- Mamba-2 paper: https://arxiv.org/abs/2405.21060
- Mamba-3 paper: https://arxiv.org/abs/2603.15569
- Mamba-3 Princeton/PLI release post and code link:
  https://pli.princeton.edu/blog/2026/mamba-3-improved-sequence-modeling-using-state-space-principles
- Official `state-spaces/mamba` repository:
  https://github.com/state-spaces/mamba
- NVIDIA empirical Mamba language-model study:
  https://arxiv.org/abs/2406.07887 and
  https://research.nvidia.com/publication/2024-06_empirical-study-mamba-based-language-models
- Hugging Face Mamba2 docs:
  https://huggingface.co/docs/transformers/en/model_doc/mamba2
- Hugging Face `state-spaces/mamba2-130m` config:
  https://huggingface.co/state-spaces/mamba2-130m/blob/main/config.json
- NVIDIA NeMo/Megatron hybrid Mamba support:
  https://developer.nvidia.com/blog/nvidia-nemo-accelerates-llm-innovation-with-hybrid-state-space-model-support/
  and
  https://docs.nvidia.com/megatron-core/developer-guide/latest/apidocs/core/core.models.mamba.mamba_model.html
- Zamba2 HF docs:
  https://huggingface.co/docs/transformers/model_doc/zamba2
- Jamba paper/docs:
  https://arxiv.org/abs/2403.19887 and
  https://huggingface.co/docs/transformers/v4.49.0/en/model_doc/jamba
- Falcon-H1 technical report and NVIDIA implementation note:
  https://arxiv.org/abs/2507.22448 and
  https://developer.nvidia.com/blog/implementing-falcon-h1-hybrid-architecture-in-nvidia-megatron-core/

Main findings:

- Mamba-2 is still the correct stable pure-Mamba family for the current
  HF/Trainer stack. It uses the SSD reformulation to get faster Mamba training
  and an attention-like grouped-head structure.
- Mamba-3 is the newest notable pure-SSM direction. It adds:
  - a more expressive exponential-trapezoidal SSM recurrence,
  - complex-valued state tracking expressed with RoPE-like rotations,
  - MIMO SSM projections for better performance without proportional decode
    latency,
  - BC/QK-style RMSNorm, and removal of the old short causal convolution.
- Mamba-3 is relevant but not yet a cheap drop-in for our current HF stack:
  the official repository says Mamba-3 requires installing the `state-spaces`
  source build, and the released implementation has newer Triton/TileLang/CuTe
  kernel assumptions. It is worth a feasibility spike, not a silent replacement
  for the current HF Mamba2 baseline.
- The strongest practical trend in language-model Mamba research is hybrid
  architecture, not pure SSM alone:
  - NVIDIA's controlled study reports pure Mamba/Mamba-2 lagging transformers
    on copying, in-context learning, and long-context reasoning tasks.
  - The same study reports Mamba-2-Hybrid, with about `43%` Mamba-2, `7%`
    attention, and `50%` MLP layers, beating the matched 8B transformer on the
    standard-task average.
  - Jamba, Zamba2, Falcon-H1, and NVIDIA Megatron/NeMo all reinforce the same
    broad direction: keep many Mamba/SSM layers for efficiency, but reintroduce
    some attention and/or MLP structure for quality and recall.
- Our repo already contains this idea:
  - `src/conf/base/mamba2_hybrid_125m.yaml`
  - `src/main/sallm/models/mamba2_hybrid.py`
  - `scripts/train_final_mamba2_hybrid.sh`
  The configured pattern is `M+M+M++M+M*+M+M++M+M*+M+`, i.e. mostly Mamba2 and
  MLP-only blocks with a small attention fraction, matching the Waleffe/NVIDIA
  direction.

Current pure-Mamba config observations:

- Current pure config (`src/conf/base/mamba_125m.yaml` and
  `scripts/run_mamba_fresh_pretrain_streaming.py`) uses:
  - `hidden_size=512`
  - `state_size=64`
  - `num_hidden_layers=27`
  - `expand=4`
  - `num_heads=32`
  - `head_dim=64`
  - `n_groups=4`
  - `tie_word_embeddings=true`
- HF `Mamba2Config` defaults and the official `state-spaces/mamba2-130m`
  shape point in a different direction:
  - HF default core knobs include `state_size=128`, `expand=2`, `n_groups=8`,
    `residual_in_fp32=true`, `rms_norm=true`, `chunk_size=256`.
  - Official `state-spaces/mamba2-130m` config uses `d_model=768`,
    `n_layer=24`, `rms_norm=true`, `residual_in_fp32=true`,
    `fused_add_norm=true`, and tied embeddings.
- Therefore our current 125M pure Mamba2 shape may be too narrow/deep and too
  high-expansion relative to the official 130M style. It may spend parameters
  differently from the stronger public recipe.

Actionable recommendation:

1. Let the active pure-Mamba LR `4e-4`, 20k pilot reach at least 10k and ideally
   20k unless it fails. It is a necessary loss-curve datapoint, but the 5k
   loss (`5.9383`) is still far from current Mamba base (`3.8066`) and LLaMA
   base (`2.3011`).
2. User correction: do not pivot to hybrid yet. Hybrid Mamba2 is important
   literature context, but the active goal remains pure Mamba/Mamba2 ("PMamba")
   optimization before architecture changes.
3. Pure Mamba2 recipe HPO should include a shape ablation closer to public
   Mamba2-130M: wider/shallower/`expand=2`/`state_size=128` against the current
   narrower/deeper/`expand=4`/`state_size=64` shape. Keep parameter count in
   the same 120-130M band and compare held-out pretraining loss per token
   budget, not only final loss.
4. Mamba-3 should not be treated as the next pretraining-quality rescue. The
   paper/blog do report quality metrics, but the main distinctive contribution
   is inference-side architecture/kernel design: richer fixed-state dynamics,
   MIMO, and decode-efficiency improvements. For this project, Mamba-3 belongs
   in a later feasibility/research bucket, not the immediate pure-Mamba
   pretraining optimization path.
5. For final reporting, separate:
   - pure Mamba2,
   - hybrid Mamba2/attention/MLP,
   - LLaMA transformer baseline,
   - future xLSTM.
   Hybrid Mamba is not the same architectural claim as pure Mamba, but it is
   likely the strongest practical SSM-family comparison point.
