## xLSTM/Mamba task interpretation and base 0-shot gap

User questions:

- Why is xLSTM strong on POS but weak on NER?
- Why is Mamba weak on both POS and NER?
- Why is xLSTM multilingual InjongoIntent much better than monolingual?
- Where are the Mamba/xLSTM base 0-shot rows for the spreadsheet?
- Have we done enough for T2X and AfriHG, and how do they compare?

Current interpretation:

- xLSTM POS vs NER is not contradictory. POS is dense, token-aligned, and
  closed-label: every token has a short tag, so the model mostly has to emit a
  stable label sequence. NER span generation is harder: entities are sparse,
  and the official task requires detecting boundaries, copying surface forms,
  preserving entity type, formatting spans correctly, and stopping cleanly.
  xLSTM diagnostic evidence shows it can learn generated token-aligned entity
  labels, but official span-copying remains weak. The completed HPO retry
  variants were also below the earlier mono Xhosa NER range, so they did not
  fix the benchmark story.
- Mamba being weak on both POS and NER looks more fundamental than the xLSTM
  NER issue. Prior tag-sequence and constrained diagnostics showed label/output
  collapse behavior even when the task was simplified, so this is not only an
  entity-span-copying problem.
- InjongoIntent mono vs multi is probably a real root-cause lead, not a result
  we should accept uncritically. The mono Xhosa validation diagnostics collapse
  into a few intents, while the multilingual variant has broader prediction
  support and much better forced-choice metrics. The likely explanation is
  label coverage/calibration: multilingual training gives many more examples
  across the shared intent label space. A defensible fix should be a bounded
  balanced-label mono canary, not a broad blind rerun.
- Base 0-shot rows were missing for both Mamba and xLSTM. The earlier
  `base_fewshot_mamba_xlstm_20260606` wave only covered 2-shot and 3-shot.
- T2X has been improved on validation for xLSTM: the mixed-source canary
  improved validation from about chrF `34.38`, BLEU `0.0712`, ROUGE-L
  `0.2949` to about chrF `39.47`, BLEU `0.0826`, ROUGE-L `0.3587`.
  This is promising but not yet an official/test result, so the fair next step
  is to promote that adapter/recipe to official test with the same comparison
  protocol.
- AfriHG remains weak semantically. xLSTM is comparable to or somewhat better
  than current Mamba on some AfriHG slices, especially Zulu/multilingual, but
  it is not clearly better than LLaMA. Treat AfriHG as still unresolved rather
  than a clean xLSTM win.

## Advisor prep: xLSTM strengths, NER/POS contrast, Mamba failures, and T2X root cause

Use this as the meeting explanation rather than treating the scores as isolated
leaderboard numbers.

### High-level thesis

- xLSTM is genuinely alive after task-specific adaptation. It is not a random
  weak model: corrected News and POS are strong, and multilingual intent is
  useful.
- The weaknesses are concentrated in tasks that require exact open-ended
  copying and structured generation: NER span extraction, T2X triple
  verbalisation, AfriHG/headline generation, and the overly broad general
  adapter.
- Mamba is different: on NER/POS it fails even when the output space is made
  simpler, which points to a more fundamental local calibration/format-learning
  problem for these token/sequence tasks at this scale.

### Why xLSTM looks strong overall

- Pretraining-side audit: held-out pretrain-style perplexity was much better
  for xLSTM than Mamba (`17.48` vs `44.99`), although still behind LLaMA
  (`9.98`). This fits the downstream pattern: xLSTM is a much stronger small
  recurrent baseline than Mamba, but not a transformer-equivalent generator.
- Corrected MasakhaNews is strong:
  - Mono corrected chat/test recheck: English F1 about `0.913`, Xhosa F1 about
    `0.920`.
  - Multilingual News: English F1 about `0.881`, Xhosa F1 about `0.919`.
  - Root cause of the earlier bad News run was eval/template path, not model
    inability.
- POS is strong under task-specific/multilingual adapters:
  - xLSTM mono Xhosa POS best parsed token accuracy: `0.813`.
  - xLSTM multilingual POS bests: Tswana `0.953`, Xhosa `0.960`, Zulu `0.967`.
- Multilingual InjongoIntent is useful where mono is weak:
  - The current interpretation is label-space coverage/calibration. The shared
    multilingual intent adapter sees more examples for the same intent labels,
    while mono can collapse on low-resource label distributions.
- Important caveat: the general adapter is not the win. General xLSTM collapses
  on structured tasks, e.g. News Xho about `0.193`, POS Xho about `0.013`, and
  NER Xho about `0.004`. The defensible story is task-specific and
  multilingual adaptation, not one universal adapter.

### Why xLSTM does well on POS but weakly on NER

The tasks look superficially similar because both are sequence labelling, but
the generation burden is different.

- POS is dense and closed-label:
  - Every token has a tag.
  - The label set is small.
  - The scorer can recover a mostly correct token-tag table even when the raw
    text is not beautiful.
- NER is sparse and copy-sensitive:
  - Most tokens are not entities.
  - The model must copy exact surface spans and attach the correct type.
  - A single missing boundary, hallucinated token, repeated entity, or wrong
    delimiter hurts F1.

Evidence:

- xLSTM multilingual POS example, Xhosa:
  - tokens: `Khange iyekelele nayo iDowns kwelayo icala .`
  - target: `VERB VERB PRON PROPN VERB NOUN PUNCT`
  - parsed xLSTM output: `VERB VERB PRON PROPN VERB NOUN PUNCT`
  - This is exactly the kind of dense token-aligned pattern xLSTM learns well.
- xLSTM mono NER best Xhosa F1 is only about `0.207` in the pulled run
  (`prompt_4`), with other prompts around `0.185` to `0.203`.
- NER example 1:
  - text includes `kukaMali`, `Fete`, and `asePunzana`.
  - target: `PER: kukaMali $$ PER: Fete $$ LOC: asePunzana`
  - xLSTM parsed output: empty.
  - Failure: it does not reliably emit sparse entity spans.
- NER example 2:
  - text includes `weYunivesithi iWalter Sisulu`, `uSibongile Mani`, `kaNSFAS`,
    `eMonti`, `ngoLwesibini`, `Hawks`.
  - target includes all of those entities.
  - xLSTM repeats `ORG: weYunivesithi`, catches some `eMonti`/`kaNSFAS`, invents
    `uMagadwa`, and misses important spans such as `uSibongile Mani`,
    `ngoLwesibini`, and `Hawks`.
  - Failure: partial copying plus repetition plus hallucinated entity strings.
- NER example 3:
  - target: `PER: UMani $$ DATE: ngoLwesibini`
  - xLSTM output: `DATE: Payment $$ PER: uMani`
  - Failure: it gets the person but hallucinates an English date value.
- Diagnostic evidence supports this mechanism:
  - In a decoder-only token-aligned NER diagnostic, xLSTM validation entity-tag
    F1/non-O recall was `0.176`, with `all_o_prediction = 0.0`.
  - So xLSTM can learn entity labels above zero; the official span task loses
    performance when exact copying and formatting are required.
- Decoding controls did not fix it:
  - Baseline lower-label NER F1 `0.114`, target-token recall `0.373`.
  - Length/repetition controls reduced runaway output but dropped F1 to `0.053`
    and target-token recall to `0.138`.
  - Therefore the problem is not simply max tokens or beam settings.

### Why Mamba is terrible on NER and POS

Mamba's NER/POS issue is more severe than xLSTM's. It is not merely a span-copy
format problem; even simplified tag-generation diagnostics fail.

- Mamba POS all-language and Xhosa task-specific runs scored `0.000` in the
  pulled official-style POS runs.
- Mamba atomic POS diagnostic, where the model only had to produce simplified
  tags, reached only about `0.208` token accuracy.
- Mamba POS example:
  - tokens: `Ndiyabazi abalandeli bethu balambele ntoni .`
  - target: `VERB NOUN PRON VERB NOUN PUNCT`
  - Mamba raw output starts with unrelated prose: `aphi In the first sentence...`
  - Parsed result: invalid, score `0`.
- Mamba atomic POS example:
  - target: `<pos_noun> <pos_verb> <pos_noun> <pos_noun> <pos_verb> <pos_punct>`
  - output: `<pos_propn> <pos_propn> <pos_verb> <pos_pron> <pos_pron>`
  - Failure: even legal-looking tag output is miscalibrated and misaligned.
- Mamba NER examples are worse:
  - For a football article with target `DATE`, `ORG`, `DATE`, Mamba outputs an
    unrelated football narrative and parses empty.
  - Another example repeats `Iyise ibhola ebaleni` many times and parses empty.
  - The longer-step/fixed Mamba NER run still only reached about `0.009` best
    F1; one example labels `NgoMgqibelo` as both `LOC` and `PER`.
- Earlier O-bias calibration was also negative:
  - best global entity F1 only `0.0019`, with `1` true positive and `411` false
    positive entities.
  - That means pushing it away from all-O did not reveal a useful boundary/type
    model; it mostly created false entities.

The advisor-safe interpretation: Mamba at this size does not learn the local
token-to-label alignment and output contract needed for these tasks under our
decoder-only prompt/eval setup. xLSTM learns the label contract for POS, but
NER's span-copy requirement remains the bottleneck.

### Why LLaMA does not share the NER failure

Use this contrast if asked whether the task itself is broken.

- LLaMA Xhosa NER best F1 is about `0.720`, far above xLSTM and Mamba.
- Example:
  - target: `DATE: ngomhla weshumi elinesibhozo kule nyanga yesiLimela $$ ORG:
    yiPirates $$ DATE: ngale njikalanga`
  - LLaMA output: the same three spans and labels.
- Another example:
  - target: `DATE: NgoMgqibelo $$ ORG: iPirates $$ ORG: iMaritzburg United $$

  - LLaMA output captures the same entity inventory, with only boundary wording
    differences such as `we-Absa Premier Soccer League` and `ozakube
    use-Orlando Stadium`.
- Therefore NER is not inherently impossible in this evaluation. The
  transformer decoder appears better at copying sparse spans and maintaining the
  delimiter/type contract.

## 18:20 SAST xLSTM POS speed diagnosis

- xLSTM is not slow because the optimized kernels are missing. The corrected
  POS log for `926181` explicitly reports that the xLSTM fast path / NX-AI
  kernels are available.
- The slowdown is in our lm-eval generation compatibility path:
  - corrected POS uses `generate_until`, so it runs `7216` generation requests;
  - `generate_xlstm_chunked` pads sequences to the xLSTM chunk boundary;
  - each generated token calls the model with `use_cache=False`;
  - the existing implementation also looped over rows one by one, which threw
    away batching for greedy generation.
- Interpretation: NX-AI kernels accelerate the forward pass, but our decode
  wrapper is still an uncached full-prefix generation loop. Mamba and LLaMA are
  much faster because their Hugging Face generation paths can use optimized
  incremental/cached decoding and preserve batching.
- Local code mitigation added for future xLSTM generation evals:
  `src/main/sallm/evaluation/xlstm_generation.py` now has a batched greedy
  path for `num_beams=1`, `do_sample=False`, `length_penalty=1.0`. This should
  help POS/tag-sequence style evals by batching active rows per token step.
  It does not affect the already-running `926181` job unless that job is
  canceled and rerun from the updated code.
